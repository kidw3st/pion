# Выкладка pionperm.ru

С октября 2026 сайт выкладывается сам. Вручную собирать и заливать архивы
больше не нужно и нельзя: ручная сборка без `build-info.json` будет отклонена.

## Как это устроено

1. Коммит в `master` запускает `.github/workflows/deploy.yml`. Задача `build`:
   решает, из какого каталога собирать (см. «Каталог в сборке»), прогоняет
   тесты (vitest и PHP) на закоммиченном снимке каталога, потом `next build`,
   проверку адресов, упаковку (`scripts/pack-build.mjs`) и проверку упакованной
   сборки теми же правилами, что на сервере (`scripts/check-server-build.php`).
   Не прошла — на сервер ничего не уходит, а запуск в GitHub Actions красный.
2. Задача `publish` кладёт в ветку `server-build` три файла: `pion-site.tar.gz`
   (сайт без `images/catalog/`), `pion-pay.tar.gz` (`server-pay/` без
   `config.php`) и `build-info.json` с sha256 обоих и с `catalog` — версией
   каталога, из которого собран сайт, временем его последней правки и числом
   букетов. Архивы воспроизводимые: при том же содержимом sha256 тот же.
3. На сервере расписание раз в 15 минут запускает `pay/deploy.php`: ISPmanager →
   «Планировщик CRON», задание «Выкладка сайта из сборки (deploy.php)»,
   `*/15 * * * *`. Он узнаёт SHA ветки, скачивает файлы по SHA, сверяет sha256,
   проверяет состав и `php -l`, раскладывает сайт и удаляет файлы прошлой сборки,
   которых нет в новой. `/pay/` обновляется, только если его архив изменился.
   Версию каталога из `build-info.json` он записывает в `state.json`
   (`current.catalogVersion`, `current.catalogChangedAt`,
   `current.catalogProducts`): по ней админка показывает «на сайте» / «ждёт
   выкладки», а ночная уборка фото решает, можно ли уносить фото в корзину. При
   каждом запуске он же проверяет каталог — см. «Сторож каталога».

От коммита до сайта — обычно 5–20 минут. Правка из админки (когда включён
переключатель) доходит до сайта обычно за полчаса: до 15 минут до запуска по
расписанию, сборка, до 15 минут до выкладки на сервере (так и написано в
строке статуса админки).

`master` — это то, что на сайте. Незаконченная работа — в отдельных ветках:
там её проверяет `ci.yml`, но никуда не выкладывает.

## Что выкладка не трогает никогда

`pay/config.php` и вообще `pay/` (кроме раскладки платёжного архива),
`blog/` (кроме нашей темы `blog/wp-content/themes/pion/`), `images/catalog/`,
`images/showcase/`, `api/showcase.json`, `.well-known/` (кроме
`.well-known/agent-skills/` — эти файлы для ИИ-ассистентов кладёт сборка).
Списки — `DEPLOY_PROTECTED` и `DEPLOY_OWNED_IN_PROTECTED` в
`server-pay/deploy-lib.php`.

## Фото каталога

`images/catalog/` из репозитория не выкладывается: эта папка принадлежит
серверу, позже туда будет загружать фото админка. Пока админки нет, новое фото
каталога надо залить на сервер вручную (ISPmanager → Менеджер файлов или
Shell-клиент) в тот же путь, на который ссылается файл данных. Фото, которое
только закоммичено в репозиторий, на сайте будет битой картинкой.

## Каталог в сборке (этап 3)

С этапа 3Б сборка умеет брать каталог не из файла в репозитории, а с сервера —
из админки. Что брать, решает переменная репозитория `CATALOG_SOURCE`. Пока она
не равна `server` (до этапа 3В так и есть), сайт собирается из снимка
`data/catalog-export.json`, как раньше. Включают её на этапе 3В; порядок — в
`docs/catalog.md`, «Для этапа 3В».

**Шаг владельца:** GitHub → Settings → Secrets and variables → Actions →
вкладка Variables → `CATALOG_SOURCE`. Переменной нет — кнопка «New repository
variable» (имя `CATALOG_SOURCE`, значение `server`); есть — измените её значение.

- не `server` (пусто, переменной нет, любое другое значение) — источник снимок;
- `server` — источник выгрузка `https://pionperm.ru/pay/catalog-export.php`
  (регистр не важен: `Server` тоже включает; пробел в значении — уже не `server`).

### Что делает запуск

`deploy.yml` запускается по коммиту в `master`, вручную («Run workflow»; из
другой ветки запуск ничего не собирает) и раз в 15 минут по расписанию (GitHub
иногда опаздывает). Решение принимает `scripts/catalog-source.mjs` (функция
`decideBuild`):

| Запуск | Источник — снимок | Источник — сервер |
|---|---|---|
| по коммиту | Собирает из закоммиченного снимка. | Скачивает выгрузку, проверяет и собирает из неё. Выгрузки нет — красный запуск, публикации нет. Выгрузка не прошла проверку — красный. |
| вручную | То же, что по коммиту. | То же, что по коммиту; с галочкой `allow_shrink` — без защиты от потери букетов. |
| по расписанию | Ничего не делает: зелёный запуск за несколько секунд. | Скачивает выгрузку. Выгрузки нет — зелёный запуск без сборки, через 15 минут попробует снова. Выгрузка не прошла проверку — красный. Коммит `master` и версия каталога те же, что в `build-info.json` последней сборки в `server-build`, — без сборки. Иначе собирает. |

- «Выгрузки нет» — сервер не ответил за 30 секунд, ответил не 200 (в том числе
  503 «Каталог ещё не создан», 403, 404) или прислал не JSON. Красным это
  делают запуск по коммиту и ручной; запуск по расписанию остаётся зелёным.
- **Из устаревшего снимка не собираем.** При источнике «сервер» и недоступной
  выгрузке запуск по коммиту красный, а не собирается из снимка в репозитории:
  снимок старше правок салона, и выкладка вернула бы на сайт старый каталог.
  Сайт остаётся на прошлой сборке. Когда сервер ответит, ближайший запуск по
  расписанию соберёт пропущенный коммит сам: он отличается от коммита прошлой
  сборки. Если выгрузка недоступна долго, а правки в админке есть, через 90
  минут придёт сообщение о каталоге (см. «Сторож каталога»).
- Прошлая сборка — `build-info.json` в ветке `server-build`. Не получилось её
  взять (ветки нет, GitHub не ответил за 2 минуты) — считается, что её нет: по
  расписанию такой запуск собирает.
- При источнике «сервер», если коммит не собирается из-за кода (красный
  `build`), запуски по расписанию краснеют вместе с ним каждые 15 минут, пока
  `master` не починят: коммит так и не стал сборкой, и они пробуют его снова.
  Так же они красны, пока выгрузка не проходит проверку (причины — в журнале
  шага «Каталог — собирать ли и из чего»; чинится в админке).
- При источнике «снимок» каждые 15 минут появляется зелёный пустой запуск
  («Источник — снимок: по расписанию собирать нечего») — так и задумано; код,
  который не собирается, краснит только запуск по коммиту или ручной.
- **Сразу после включения переключателя запуск по расписанию может ничего не
  собрать.** Версия каталога — хэш содержимого. Если в базу загружено то же
  содержимое, что в снимке, версии равны, а коммит тот же, что в прошлой сборке,
  — запуск по расписанию заканчивается «ни код, ни каталог не изменились» и
  `--status` на сервере ничего нового не покажет. Первую сборку с сервера
  запускают вручную («Run workflow»): ручной запуск собирает всегда.

### Защита от потери букетов и `allow_shrink`

Выгрузка, в которой букетов меньше 70% от числа в прошлой сборке
(`catalog.products` в её `build-info.json`), не принимается: запуск красный, в
журнале «Букетов N вместо M — меньше на …%». Это защита от выкладки
полупустого каталога.

Если салон и правда удалил столько букетов — *шаг владельца:* GitHub → Actions
→ «Сборка и выкладка» → «Run workflow» → ветка `master` → отметить «Букетов
стало намного меньше — так и задумано…» → Run. Галочка `allow_shrink` включает
флаг `--allow-shrink` у `apply-catalog-export.mjs` и действует только на этот
запуск; следующие сверяют уже с новым числом. При источнике «снимок» она ни на
что не влияет. Если запуск с галочкой вытеснили из очереди (см. ниже) или его
снял новый коммит, галочка пропала — запустите ещё раз.

Защиты нет, когда числа не с чем сравнить: в `build-info.json` прошлой сборки
нет `catalog.products` (первая сборка с сервера после сборки без каталога) или
прошлую сборку не удалось взять. В журнале запуска тогда «Внимание: защиты от
потери нет — в прошлой сборке нет числа букетов.»

### Очередь запусков и переключение

Запуски `master` стоят в одной очереди (`concurrency` в `deploy.yml`) и
занимают место в момент появления. Новый коммит отменяет идущий запуск (в нём
есть всё). Ручной запуск и запуск по расписанию идущий не отменяют, а ждут его
конца вместе с публикацией. Ждать может только один запуск: более новый
вытесняет ожидающего, и тот в Actions отменён. Запуск по расписанию при
источнике «снимок» в очередь не встаёт (у него своя группа на один запуск) и
никого не вытесняет.

Очередь запуск выбирает при создании, а значение `CATALOG_SOURCE` читает
чуть позже. Поэтому включайте и выключайте переключатель, только когда в
Actions нет идущих и ожидающих запусков «Сборка и выкладка»: запуск, созданный
на стыке, мог бы собираться вне очереди, параллельно с коммитом (две
публикации могут разойтись), или вытеснить ожидающую сборку коммита.

Выключили — убедитесь, что последний коммит `master` выложен: на сервере
`php deploy.php --status`, строка «Выложена сборка … (коммит …)». Не выложен —
«Run workflow»: запуск по расписанию его больше не подхватит. И помните, что
выключение не откатывает каталог: следующая сборка по коммиту возьмёт снимок из
репозитория, и правки, сделанные в админке после снимка, пропадут с сайта (в
базе они останутся).

### Расписание не засыпает (`keepalive.yml`)

GitHub выключает запуски по расписанию в публичном репозитории после 60 дней
без коммитов, и правки из админки перестали бы доходить до сайта. Поэтому
`keepalive.yml` 1-го числа каждого месяца (04:17 UTC) заново включает
`deploy.yml` и самого себя. Побочное действие: если вы сознательно выключили
«Сборку и выкладку» в Actions, 1-го числа она включится снова.

### Что получают сервер и админка

`pack-build.mjs` пишет в `build-info.json` блок `catalog`: `version` (sha256
выгрузки), `changedAt` и `products`. Время должно быть в виде
`2026-10-05T14:32:10+05:00` (как у `catalog_iso`) или `null`, если каталог ещё
не менялся; другое (например, `…:10.000Z`) останавливает сборку. `deploy.php`
переносит блок в `state.json` как есть. Админка время только читает: мусор она
считает неизвестным (отметки «на сайте» у правок пропадают, страницы не
падают). Читает она мягче сборки (`Z` и `+0500` примет, `.000Z` нет), поэтому
контракт держит сборка, а не админка.

### Сторож каталога

Каждый запуск `deploy.php` без аргументов (по расписанию раз в 15 минут или
вручную) читает папку каталога (`pion-catalog/`) и при необходимости пишет в тот
же служебный чат.
Нет файла базы `catalog.sqlite` — сторож каталога молчит совсем. Файл есть, но
база не открывается или новее кода — молчит только сообщение `catalog` (в
`deploy.log` строка «не прочитать базу каталога для сторожа: …»), а о копиях и
обслуживании сторож пишет как обычно. `--dry-run`,
`--rollback` и `--status` базу не читают и ничего не отправляют. Одно и то же
сообщение приходит не чаще раза в 3 часа, кроме сообщений о копии (раз в
сутки) и об обслуживании (раз на каждый неудавшийся запуск).

| Сообщение | Когда приходит | Как часто |
|---|---|---|
| «Каталог pionperm.ru: изменения из админки больше 90 минут не на сайте…» (`catalog`) | Версия каталога в базе не равна `current.catalogVersion` в `state.json`, и последняя правка старше 90 минут. Часы скользящие: каждая новая правка отсчитывает 90 минут заново. Молчит, если выкладка сбоит (тогда приходит сообщение о сбое), если на сайте ещё нет версии каталога (сборка без каталога) и если в базе нет ни одной правки. | Раз в 3 часа, пока сборка не выложена. |
| «Каталог pionperm.ru: свежей копии базы нет больше двух суток…» (`backup`) | В `pion-catalog/backups/` нет ни одной копии `catalog-*.sqlite` или самая свежая старше двух суток (по времени файла). Приходит и при сбое выкладки. Копий нет совсем — уже на ближайшем запуске. | Раз в сутки. |
| «Каталог pionperm.ru: ночное обслуживание не удалось — …» (`maintenance`) | В `pion-catalog/maintenance.json` `ok: false`. Итог пишет `maintenance-cli.php` (см. `docs/catalog.md`, «Расписание и обслуживание»). Причина — первая строка итога, до 300 знаков. | Один раз на каждый неудавшийся запуск (по времени `at` в итоге). |

Если одновременно не собрался коммит и не дошёл каталог, придут оба сообщения:
про коммит («больше 90 минут не превращается в сборку») и про каталог. После
`--rollback` сообщение о каталоге отправит в GitHub Actions, но причина другая:
сервер отказывается выкладывать откатанную пару «код + каталог» (см. «Откат»).

## Если что-то пошло не так

Сообщения приходят в Telegram, в чат `DEPLOY_ALERT_CHAT_ID` из `config.php`. Это
личный чат владельца с ботом заказов: туда же приходят и заказы. Салону
служебные сообщения не уходят.

- **Красный запуск в GitHub Actions** (письмо от GitHub) — на сервер ничего не
  ушло, сайт не менялся. Откройте запуск и посмотрите, какая задача красная.
  `build` — исправить код и закоммитить снова. `publish` (сборка не легла в
  `server-build`, обычно сбой GitHub) — «Re-run failed jobs» на странице запуска.
  При `CATALOG_SOURCE=server` `build` краснеет и из-за каталога — смотрите журнал
  шага «Каталог — собирать ли и из чего». «Выгрузка не принята:» и список —
  выгрузка не прошла проверку: причины названы, исправляются в админке, следующий
  запуск по расписанию (до 15 минут) соберёт сам. «Сервер не отдал выгрузку — из
  устаревшего снимка не собираем» — `/pay/catalog-export.php` не отвечает или
  отвечает ошибкой (в том числе 503, пока база пуста): проверьте адрес; сайт
  остаётся на прошлой сборке, коммит выложится, когда выгрузка вернётся.
- **«Выкладка pionperm.ru остановлена: сборка XXXXXXX не прошла проверку — …»**
  Сервер отклонил сборку: не хватает файлов, ошибка синтаксиса PHP, файлы в
  чужих путях или «в ветке server-build не хватает файлов … 404». Причина — в
  конце сообщения. Сайт работает на прежней сборке. Эта сборка помечена плохой и
  больше не пробуется: исправьте код и закоммитьте. Чтобы выложить тот же код без
  изменений — GitHub → Actions → «Сборка и выкладка» → «Run workflow» (получится
  новая сборка). В `deploy.log` и при ручном запуске это же событие называется
  «сборка … отклонена».
- **«Выкладка pionperm.ru: больше часа не получается выложить новую сборку — …»**
  Обычно недоступен GitHub или сеть хостинга, и проходит само: сервер пробует
  каждые 15 минут. Причина — в конце сообщения. Если тянется часами —
  `php deploy.php --status` и `deploy.log`: помешать могут диск, права, `tar` или
  `php`.
- **«Выкладка pionperm.ru: коммит XXXXXXX в master больше 90 минут не превращается в сборку. Проверьте GitHub Actions.»**
  Сборка на GitHub упала или не началась: GitHub → Actions.
- **«Каталог pionperm.ru: изменения из админки больше 90 минут не на сайте. Проверьте GitHub Actions («Сборка и выкладка»).»**
  Правка сохранена в базе, а выложенная сборка собрана из прежнего каталога.
  GitHub → Actions: нет ли красного или ожидающего запуска (причины красных — выше).
  Красных нет — `php deploy.php --status` и `deploy.log`: сервер мог отказаться от
  сборки («повторяет откатанную сборку», см. «Откат») или не успеть её забрать.
  Проходит само, когда сборка с этой версией каталога выложена.
- **«Каталог pionperm.ru: свежей копии базы нет больше двух суток — проверьте задание обслуживания.»**
  Не работает задание `maintenance-cli.php` (оно же делает копию). ISPmanager →
  «Планировщик CRON»: задание есть? Потом в `/var/www/u3620798/data/pion-catalog/`:
  `tail -5 maintenance.log` — когда был последний запуск и чем кончился — и
  `ls -t backups | head -3` — какие есть копии. Напоминание повторяется раз в сутки.
- **«Каталог pionperm.ru: ночное обслуживание не удалось — …»**
  Причина — в конце сообщения (первая строка итога, до 300 знаков); весь итог —
  в `pion-catalog/maintenance.json`, история запусков — в `maintenance.log`. Чаще
  всего это «Уборка фото остановлена… нужна проверка разработчика» (см.
  `docs/catalog.md`). Исправили причину — запустите `php maintenance-cli.php` в
  `pay/catalog` ещё раз: итог перезапишется на «ok». Сообщение приходит один раз
  на каждый неудавшийся запуск и не повторяется, пока не будет нового.
- **«Выкладка pionperm.ru: deploy.php упал — …»**
  Сломался сам deploy.php: например, не записывается `state.json` или кончилось
  место на диске. Приходит не чаще раза в час. Смотрите `deploy.log` и запустите
  `php deploy.php` вручную — ошибка появится на экране. Если сломан сам файл —
  см. «Если сломан сам deploy.php».
- **Выложилось, но сломалось** — см. «Откат».
- **Пересобрать без изменений кода** — GitHub → Actions → «Сборка и выкладка» →
  «Run workflow» (ветка `master`).
- **Сообщений нет, а сайт не обновился** — см. «Тишина».

## Откат

Выложилось, но сайт сломан — вернуть прошлую сборку:

    cd /var/www/u3620798/data/www/pionperm.ru/pay
    php deploy.php --rollback

**Эта команда меняет боевой сайт.** Она возвращает предыдущую сборку вместе с
её каталогом, а текущую помечает плохой двумя способами: по номеру сборки в
`server-build` (`bad`) и по паре «код + каталог» (`badPairs`: полный коммит
кода из `master` и версия каталога, из которого собран сайт). Откат возможен,
пока `--status` пишет «Для отката хранятся: …» (хранятся две прошлые сборки).

Пара нужна потому, что пересборка («Run workflow», запуск по расписанию) кладёт
в `server-build` сборку с новым номером, но с тем же коммитом и тем же
каталогом. Номер новый, пара прежняя — и сервер такую сборку не выкладывает: в
`deploy.log` «сборка XXXXXXX не выложена: повторяет откатанную сборку (код …,
каталог …)», а `--status` показывает её строкой «Не выкладывать XXXXXXX: …».
Сообщения в Telegram об отказе нет. Помнятся 20 последних пар.

Пара защищает, только пока не изменилось ни одно из двух. Новый коммит в
`master` или новая версия каталога после правки в админке — это уже другая
пара, и она выложится.

После отката:

- **Ошибка в коде.** В `master` всё ещё лежит плохой код. Отмените его сразу,
  до следующего коммита и до следующей правки каталога (при `CATALOG_SOURCE=server`
  её подхватит ближайший запуск по расписанию, и плохой код выложится с новой
  парой): `git revert <коммит>` и push. Номер коммита — в `--status` до отката,
  в строке «Выложена сборка … (коммит …)».
- **Ошибка в каталоге** (сайт сломала сама выгрузка). Исправьте каталог в
  админке: исправленный каталог — другая версия, значит другая пара, и он
  выложится обычным порядком.
- Откат возвращает и прежний каталог: правки салона, сделанные после той сборки,
  на сайте пропадут до следующей выкладки (в базе они остаются). Админка
  пишет «Ждёт выкладки», уборка фото ничего не уносит в корзину (версия базы не
  совпадает с выложенной), а через 90 минут после последней правки сторож
  напишет про каталог и отправит в GitHub Actions, хотя причина здесь в отказе
  сервера (см. выше).
- Файлы, которые плохая сборка добавила в `/pay/`, остаются: `/pay/`
  накладывается и не чистится. Если они мешают, удалите их вручную.
- Если откат не удался («Откат не удался: …»), сайт мог измениться частично.
  Запустите откат ещё раз.

**Снять пометку.** Отдельной команды нет. Нужно выложить откатанную пару ещё раз
(откат был зря) — два способа:

1. Пустой коммит в `master` (`git commit --allow-empty`, push). У него другой
   коммит, значит другая пара.
2. Правка `/var/www/u3620798/data/pion-deploy/state.json`: удалить пару из
   `badPairs` (ключ вида `<коммит>|<версия каталога>`) и сборку из `bad`. Сначала
   сделайте копию файла: если после правки JSON не читается, deploy.php начнёт с
   пустого состояния.

## Тишина

Коммит не появился на сайте через полчаса после зелёного запуска в GitHub, а
сообщения не пришло:

    cd /var/www/u3620798/data/www/pionperm.ru/pay
    php deploy.php --status
    tail -20 /var/www/u3620798/data/pion-deploy/deploy.log
    crontab -l

1. `--status` — какая сборка выложена и нет ли сбоя.
2. `deploy.log` — когда deploy.php запускался в последний раз. Свежих строк
   нет — расписание не работает.
3. `crontab -l` — задание должно быть в списке. Оно живёт в ISPmanager →
   «Планировщик CRON»: «Выкладка сайта из сборки (deploy.php)», `*/15 * * * *`.
   Нет задания — создайте его заново (полный путь к `php` и к `pay/deploy.php`).
4. `php deploy.php` — запустите выкладку вручную и прочитайте, что она пишет.
   «Другая выкладка ещё идёт.» — прошлый запуск не кончился, подождите минуту.
   «Не открыть …/deploy.lock — проверьте права на папку pion-deploy.» — исправьте
   права на `/var/www/u3620798/data/pion-deploy/`.

Почему сообщения может не быть: deploy.php проверяет себя сам и не может
сообщить о собственной смерти. Нет задания в планировщике, не запускается PHP,
сломан сам файл — он молчит. А панель отправляет вывод cron в `/dev/null`, так
что и ошибки нигде не видно.

## Если сломан сам deploy.php

deploy.php обновляется вместе с `/pay/`, поэтому исправление, которое вы
выложили в `master`, не дойдёт до сервера через сломанный deploy.php. Чинить
надо вручную, из хорошей сборки, которая хранится на сервере:

    ls -t /var/www/u3620798/data/pion-deploy/releases
    tar -xzf /var/www/u3620798/data/pion-deploy/releases/<sha>/pion-pay.tar.gz -C /var/www/u3620798/data/www/pionperm.ru/pay/

`<sha>` — папка сборки, при которой deploy.php ещё работал: обычно предыдущая
(`ls -t` показывает новые первыми, а первые 7 символов совпадают с номерами в
`--status`). `config.php` в этих архивах не бывает, распаковка его не трогает.

Нет подходящей сборки — скопируйте нужные файлы из резервной копии
`/var/www/u3620798/data/pay-backup-*`. `config.php` при этом не перезаписывайте.
