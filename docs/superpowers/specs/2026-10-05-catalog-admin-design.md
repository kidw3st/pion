# Админка каталога и автовыкладка pionperm.ru — дизайн

Дата: 2026-10-05

## Контекст

На Tilda салон сам добавлял букеты в разные разделы каталога. После переезда
на собственный сайт (Next.js, статический экспорт, хостинг reg.ru) каталог —
это файлы `data/catalog/*.json`, один раз выгруженные из Tilda в августе.
Сайт собирает и выкладывает разработчик. Сам по себе обновляется только блок
«Букеты в наличии»: PHP-скрипт по расписанию забирает витрину из Posiflora.

Поэтому любое изменение каталога — новый букет, другая цена, снятие с
продажи — сейчас идёт через разработчика.

## Цель

Салон сам ведёт весь каталог сайта: добавляет, меняет и снимает букеты,
создаёт разделы. Изменения попадают на сайт без участия разработчика, у
каждого букета своя страница со своим адресом.

## Решения, принятые с владельцем

| Вопрос | Решение |
|---|---|
| Где вести каталог | Своя админка на сайте. Posiflora не подходит: её категории складские («Гербера», «Пакеты»), публичного каталога с разделами там нет. |
| Защита | Вход по логину и паролю, у каждого сотрудника свой. Адрес нигде не публикуется и закрыт от поисковиков, но защищает именно пароль: через админку меняются цены, по которым сервер выставляет счёт. |
| Какие букеты в админке | Все: и перенесённые из Tilda, и новые. |
| Как появляются страницы | Автосборка: при изменении каталога сайт пересобирается целиком. Страницы полноценные, как сейчас, со всей разметкой для поисковиков. |
| Разделы | Салон создаёт и скрывает разделы сам (сезонные коллекции и т. п.). |
| Нет в наличии | «Снять с продажи»: букет пропадает из разделов, заказать его нельзя, страница остаётся с пометкой «Сейчас нет в продаже». «Вернуть в продажу» ставит его на прежнее место по тому же адресу. |
| Черновики | Есть. Букет можно подготовить заранее: до публикации его на сайте нет совсем. Добавлено по просьбе салона 2026-10-05. |
| «Новинки» на главной | Ведутся из админки как раздел «Новинки»: первые три букета в продаже из него показываются на главной. Добавлено по просьбе салона 2026-10-05. |
| Где собирать сайт | На GitHub Actions. На хостинге нельзя: Node.js недоступен (`node` требует прав суперпользователя), лимит памяти процесса 256 МБ, а сборке нужно около гигабайта. Публичной копии сайта на GitHub нет и не будет. |

## Что есть сейчас

Цифры проверены 2026-10-05.

**Каталог**
- 13 разделов, 522 записи. Сайт пропускает их через `dedupeProducts` (убирает «Copy: …» и вторые копии) и показывает 487 товаров. Каждый товар лежит ровно в одном разделе.
- У 378 из 487 товаров стоит `published: false` — это флажок из Tilda. Сайт его сознательно не учитывает (`ONLY_ACTIVE_IN_STORE = false`): показывает и продаёт весь ассортимент.
- Адрес товара — `/<раздел>/<slug>/`. Slug получен из названия функцией `slugify` (`scripts/import-tilda-csv.mjs`: «ы» → `y`, не длиннее 60 знаков). Правилу соответствуют 486 из 487 адресов. Три slug повторяются в двух разделах (`pion`, `nezhnost`, `roza-nina`) — это разные товары.
- В сетке каталога 12 плиток: 8 разделов и 4 постоянные — «Цветы» (`/flowers`), «Комнатные растения» (`/indoorflowers`), «Букеты до 5000» (`/bukety-do-5000`), «Создать уникальный букет» (всплывающее окно). У пяти разделов плитки нет (`pions`, `roses`, `mixflower`, `valentinesday`, `new-year-2025`), но страницы есть.
- Поштучные цветы — тоже разделы каталога: «Розы» (`roses`), «Пионы» (`pions`), «Разные цветы» (`mixflower`). На них ведут три плитки страницы «Цветы» (`data/pages/flowers.json`).
- Блок «Новинки» на главной — три карточки из `data/site.json` (`newProducts`): название, подпись, цена, фото. Своих страниц у них нет. Их цены продублированы на сервере в `config.php` (`EXTRA_ITEMS`), иначе их нельзя оплатить.
- Названия разделов заданы в коде (`CATEGORY_SLUGS`, `CATEGORY_LABELS` в `src/lib/content.ts`), обложки и тексты над сеткой — в `data/catalog-meta.json`, особые SEO-заголовки части разделов — в `PAGE_SEO` (`src/app/[slug]/page.tsx`).
- Фото: один файл на снимок, `images/catalog/<раздел>/<slug>-<uid>[-n].webp`, до 900 px по ширине, WebP качества 82, около 150 КБ. Всего 59 МБ, лежат в git и уезжают в архиве сайта.
- В карте сайта 515 адресов.
- При оплате `price_order()` берёт цены через `catalog_index()` из `api/catalog/*.json` выложенной сборки. Неизвестный uid — ошибка «Товар не найден».

**Выкладка.** Разработчик собирает сайт у себя, кладёт архивы в ветку
`server-build` и раскладывает их на сервере вручную, скачивая по SHA коммита.
В расписании сервера осталось временное задание «Обновление сайта из сборки»
(`0 0 * * *`): каждую полночь оно скачивает сборку по адресу ветки, без
привязки к SHA, — и может получить из кэша GitHub устаревший архив.

**Хостинг**
- PHP 8.2 (CLI 8.2.33), `pdo_sqlite`, `sqlite3`, `gd` с `imagewebp`. Imagick нет.
- `upload_max_filesize = 2M`, `post_max_size = 8M` — фото с телефона в лимит не влезают.
- Лимиты процесса: память 256 МБ, процессорное время 900 с, до 36 процессов.
- Сервер достаёт `api.github.com` и `raw.githubusercontent.com`. Доступ к `github.com` проверяется на этапе 1.
- Расписание (cron) работает: витрина синхронизируется каждые 15 минут.
- Правила от парсеров в `.htaccess` отклоняют «голые» скрипты (`python-requests`, `go-http-client`, `wget` и т. п.) везде, кроме `/pay/`.

## Архитектура

```
 Админка (PHP, /pay/admin/)
   │ «Сохранить»
   ▼
 База каталога на сервере (SQLite, вне веб-корня)
   │ отдаётся по адресу /pay/catalog-export.php
   ▼
 GitHub Actions в kidw3st/pion — раз в 15 минут и при изменении кода:
   выгрузка или код изменились? → тесты → next build → проверки адресов
   │
   ▼
 Ветка server-build: архивы сайта и /pay/, build-info.json
   │ раз в 15 минут сервер проверяет, нет ли новой сборки
   ▼
 deploy.php на сервере: скачивает по SHA → проверяет → раскладывает → чистит устаревшее
   ▼
 pionperm.ru
```

**На сервере нет ни одного ключа от GitHub.** GitHub сам забирает каталог с
сервера, сервер сам забирает сборку с GitHub. Взлом хостинга не даёт доступа
к коду сайта.

**Время.** От «Сохранить» до сайта обычно 15–30 минут: до 15 минут до
проверки на GitHub, 3–5 минут сборка, до 15 минут до проверки сервером.
GitHub иногда запаздывает с запусками по расписанию, тогда до 45 минут.
Салону обещаем «примерно полчаса».

**`master` — это то, что на сайте.** Всё, что попало в `master` и прошло
проверки, само уезжает на сайт. Незаконченная работа живёт в отдельных
ветках.

## Компоненты

### 1. Админка

PHP, страницы рисуются на сервере. JavaScript нужен только для уменьшения фото
перед отправкой. Рассчитана на телефон: флористы работают с телефона.

**Адрес** — `https://pionperm.ru/pay/admin/`. Ссылок на него на сайте нет.
Весь `/pay/` уже закрыт в `robots.txt`, отдельной строки для админки там нет.
Все ответы админки идут с `X-Robots-Tag: noindex, nofollow` и
`Cache-Control: no-store`.

**Экраны**

- **Вход.** Логин и пароль. При первом входе админка просит сменить начальный пароль.
- **Букеты.** Список с поиском по названию и фильтрами: раздел, «в продаже» / «снят» / «черновик» / «удалённые». Кнопка «Добавить букет».
- **Карточка букета**
  - название (до 120 знаков), цена в рублях (целое число), состав (до 1000 знаков);
  - до 4 фото: загрузить, поменять порядок, удалить; первое — главное;
  - разделы — галочки, можно несколько. Один из отмеченных — **главный**: по нему строится адрес страницы. По умолчанию главный — первый отмеченный по списку разделов, кроме «Новинок»: новизна проходит, а адрес должен остаться;
  - адрес страницы — только для чтения;
  - кнопки зависят от статуса:
    - черновик — «Сохранить черновик», «Опубликовать», «Удалить»;
    - в продаже — «Сохранить», «Снять с продажи», «Удалить»;
    - снят — «Сохранить», «Вернуть в продажу», «Удалить»;
    - удалён — «Восстановить» (90 дней после удаления).

  Удаление и снятие с продажи — с подтверждением. Опубликованный букет в
  черновик не возвращается: его страница уже известна поисковикам, и вместо
  неё была бы ошибка 404. Для этого есть «Снять с продажи».

  Если создают букет с названием, которое уже есть у снятого или удалённого,
  админка предлагает вернуть прежний: «Такой букет уже был — снят с продажи
  12 марта. Вернуть его?». Так не появляются две одинаковые страницы.
- **Разделы.** Порядок плиток в каталоге и кнопка «Создать раздел». Карточка раздела:
  - название — оно же подпись плитки, хлебные крошки и заголовок для поиска по шаблону;
  - фото плитки;
  - «Показывать в каталоге» — есть ли у раздела плитка. Скрытый раздел пропадает из сетки, но его страница остаётся;
  - под «Дополнительно» — обложка (заголовок, подзаголовок, до 3 фото), заголовок над сеткой, блок «Не нашли нужное?», SEO-заголовок и описание. Пустые SEO-поля — значит, по шаблону.

  Удалить раздел нельзя, только скрыть: у страницы раздела копятся позиции в поиске.

  Четыре постоянные плитки («Цветы», «Комнатные растения», «Букеты до 5000», «Создать уникальный букет») можно только двигать.

  **«Новинки»** — обычный раздел с одной особенностью: первые три букета в
  продаже из него стоят на главной в блоке «Новинки», с пометкой NEW и
  ссылкой на страницу букета. Чтобы букет попал на главную, достаточно
  отметить у него «Новинки»: добавленный в раздел встаёт первым. Плитки в
  каталоге у «Новинок» по умолчанию нет, страница `/novinki/` есть, как у
  любого раздела.
- **Журнал.** Кто, когда и что поменял: было → стало. Последние 500 изменений.
- **Смена пароля.**

**Статус выкладки** — строка вверху каждого экрана:
«Все изменения на сайте» / «Ждёт выкладки с 14:32 — обычно до получаса» /
«Выкладка задерживается — разработчик уведомлён». В журнале и в карточке
букета у каждого изменения своя отметка: «на сайте» или «ждёт выкладки».
Изменение на сайте, если оно не позже `changedAt` выложенной сборки (см.
раздел 3).

**Учётные записи** заводит разработчик скриптом на сервере. Скрипт сам
придумывает начальный пароль и показывает его один раз. Роли одинаковые.

**Фото.** Браузер уменьшает снимок до 2000 px по длинной стороне и
отправляет JPEG, каждый снимок отдельным запросом, — так он укладывается в
лимиты хостинга (2 МБ на файл, 8 МБ на запрос). Сервер
открывает файл через GD (не открылся как изображение — отказ), уменьшает до
900 px по ширине и сохраняет WebP качества 82 — те же параметры, что у
нынешних фото (`scripts/optimize-images.mjs`). Имя файла —
`<slug>-<uid>-<8 знаков хэша>.webp` в папке `images/catalog/<главный раздел
на момент загрузки>/`. Новое фото — новое имя: фото кэшируются на 30 дней, и
под старым именем браузеры показывали бы прежний снимок. При смене раздела
файлы не переезжают.

**Проверка цены.** Пустая, меньше 100 ₽ или больше 300 000 ₽ — не
сохраняется. Если цена изменилась больше чем вдвое, админка переспрашивает:
«Цена была 4 400 ₽, станет 44 000 ₽. Всё верно?».

**Одновременная правка.** Если букет, пока его редактировали, сохранил
кто-то другой, повторное сохранение не затирает чужую правку. Админка
сообщает: «Этот букет только что изменила Анна — откройте его заново».

### 2. База каталога

SQLite-файл вне веб-корня: `/var/www/u3620798/data/pion-catalog/catalog.sqlite`.
Через сайт его не скачать.

Таблицы:

- `sections` — slug (ключ), название, фото плитки, показывать в каталоге, порядок плитки, заголовок и подзаголовок обложки, фото обложки (JSON), заголовок и подзаголовок над сеткой, «Не нашли нужное?», SEO-заголовок, SEO-описание, когда изменён.
- `tiles` — постоянные плитки: подпись, адрес, фото, порядок.
- `products` — uid (ключ), slug, название, состав, цена, фото (JSON), главный раздел, статус (`draft` / `active` / `hidden` / `deleted`), когда создан, изменён, впервые опубликован и удалён.
- `product_sections` — в каких разделах букет и на какой позиции.
- `redirects` — откуда → куда.
- `users` — логин, имя, хэш пароля (`password_hash`), нужно ли сменить пароль.
- `audit` — время, логин, объект, поле, было, стало.
- `login_attempts` — IP, логин, время.

Каждое сохранение — одна транзакция.

**Правила данных**

- **Статусы.** `draft` — черновик: на сайте его нет совсем, ни страницы, ни места в разделах. `active` — в продаже. `hidden` — снят: страница с пометкой «Сейчас нет в продаже», в разделах не показывается, заказать нельзя. `deleted` — удалён: страницы нет, с адреса переадресация на главный раздел. Удалённый черновик просто исчезает: на сайте его не было.
- **Uid нового букета** — 12 случайных цифр, как у перенесённых из Tilda. Не совпадает ни с одним uid в базе, включая удалённые: uid остаётся в истории заказов.
- **Slug** — из названия той же функцией `slugify`, перенесённой в PHP. У черновика slug следует за названием: адрес ещё никто не знает. При первой публикации slug закрепляется и дальше не меняется, даже если букет переименовать. Закреплённый slug уникален среди опубликованных букетов всего каталога: занят — добавляется `-2`, `-3`.
- **Снять и вернуть** — один и тот же букет: адрес, uid, фото и место в разделах не меняются.
- **Смена главного раздела** меняет адрес на `/<новый раздел>/<slug>/`, а со старого адреса появляется переадресация. Если в новом разделе такой адрес уже занят (бывает только у трёх старых одноимённых пар), админка не даёт сделать раздел главным. Добавить букет в этот раздел вторым можно.
- **Удаление** ставит статус `deleted`, запись остаётся в базе. 90 дней букет можно восстановить: вернутся адрес, фото и разделы, переадресация снимется. Если за это время адрес занял другой букет, восстановленный получит адрес с `-2`.
- **Адрес удалённого букета** может занять новый букет с тем же названием в том же главном разделе — переадресация с адреса снимается, и страница снова живая.
- **Цепочки переадресаций** схлопываются: A → B и B → C превращаются в A → C. Если адрес снова занят живой страницей, переадресация с него снимается.
- **Букет встаёт первым в разделе**, когда его туда добавили или когда его опубликовали из черновика.
- **Slug раздела** — из названия, уникален и не совпадает с занятыми адресами сайта: `catalog`, `checkout`, `v-nalichii`, `bukety-do-5000`, `blog`, `pay`, `api`, `images`, `md`, `fonts`, `_next`, `tproduct`, `tstore` и `PAGE_SLUGS`. Вторая линия защиты — сборка: она падает, если раздел совпал с другой страницей.

### 3. Выгрузка каталога

`GET /pay/catalog-export.php` отдаёт весь каталог одним JSON. Адрес под
`/pay/`, поэтому правила от парсеров его не задевают, а `robots.txt` его уже
закрывает.

Ключа нет: в выгрузке только то, что и так окажется на страницах сайта.
Снятые букеты и скрытые разделы страницы сохраняют. Пользователей, журнала,
черновиков и удалённых букетов в выгрузке нет.

```json
{
  "version": "sha256 содержимого",
  "changedAt": "2026-10-05T14:32:10+05:00",
  "sections": [
    { "slug": "bukety", "label": "Букеты", "tileImage": "/images/…",
      "visible": true, "coverTitle": "Букеты", "coverSub": "…",
      "covers": ["/images/…"], "heading": "БУКЕТЫ", "headingSub": "…",
      "hasNotFound": true, "seoTitle": null, "seoDescription": null,
      "products": ["553645466981", "…"] }
  ],
  "tiles": [
    { "type": "link", "label": "Цветы", "href": "/flowers", "image": "/images/…" },
    { "type": "section", "slug": "bukety" },
    { "type": "popup", "label": "Создать уникальный букет", "href": "#popup:individual", "image": "/images/…" }
  ],
  "products": [
    { "uid": "553645466981", "slug": "buket-barhatnye-grani",
      "title": "Букет «Бархатные грани»", "description": "Состав букета: …",
      "price": 6380, "images": ["/images/catalog/bukety/…webp"],
      "mainSection": "bukety", "status": "active" }
  ],
  "redirects": [ { "from": "/korobki/buket-x/", "to": "/bukety/buket-x/" } ]
}
```

`tiles` перечислены в порядке сетки, скрытые разделы в неё не попадают.
`sections[].products` — все букеты раздела в его порядке, включая снятые:
снова поставленный в продажу букет возвращается на своё место. Версия —
sha256 от содержимого в каноническом виде, без `changedAt`: одинаковый
каталог всегда даёт одинаковую версию. `changedAt` — время последнего
сохранения в админке; сборка переносит его в `build-info.json`, а оттуда он
попадает в состояние выкладки.

### 4. Сборка на GitHub Actions

Новый workflow `.github/workflows/deploy.yml` в `kidw3st/pion`.

**Запуски:** раз в 15 минут по расписанию, при push в `master`, вручную.
Одновременно идёт только один запуск, следующий ждёт в очереди.

**Шаги**

1. Скачать выгрузку с `pionperm.ru`. Сервер не ответил — запуск заканчивается без сборки и без ошибки, через 15 минут будет следующий.
2. Сравнить версию выгрузки и коммит `master` с `build-info.json` в ветке `server-build`. Ничего не изменилось — конец. Обычный холостой запуск занимает около 30 секунд.
3. **Проверить выгрузку** (`scripts/apply-catalog-export.mjs`): uid уникальны; главный раздел есть среди разделов букета; пары «раздел + slug» уникальны; цены целые и положительные; разделы букетов существуют. Защита от массовой потери: если букетов на 30% меньше, чем в прошлой сборке, сборка останавливается. Если салон действительно столько удалил, разработчик запускает её вручную с флагом `allow_shrink`.
4. Записать данные для сборки: `data/catalog/<раздел>.json`, `data/catalog-meta.json`, `data/redirects.json`.
5. `npm ci`, `npm test`. PHP 8.2 — та же версия, что на хостинге: `php -l` для всех файлов `server-pay/` и PHP-тесты.
6. `npm run build` с `SITE_URL=https://pionperm.ru`. `postbuild` проверяет адреса, как сейчас: любое упоминание `github.io` роняет сборку.
7. Упаковать:
   - `pion-site.tar.gz` — `out/` без `images/catalog/`: фото каталога живут на сервере, их загружает админка;
   - `pion-pay.tar.gz` — `server-pay/` без `config.php`;
   - `build-info.json` — коммит кода, версия каталога и её `changedAt`, время сборки, число букетов, sha256 обоих архивов.
8. Положить их одним коммитом в ветку `server-build` (force-push, как сейчас). Права workflow — `contents: write` и `actions: write`. Прав на публикацию Pages нет.
9. Продлить расписание. GitHub отключает расписание в публичном репозитории после 60 дней без активности, поэтому раз в 50 дней workflow включает себя заново через API.

`ci.yml` остаётся для веток и pull request: проверку `master` берёт на себя
`deploy.yml`.

### 5. Выкладка на сервер

`pay/deploy.php` по расписанию раз в 15 минут вместо старого полуночного
задания. Через браузер его не запустить: закрыт в `pay/.htaccess`, как
`sync-showcase.php`.

1. Взять блокировку. Если идёт другая выкладка — выйти.
2. Узнать SHA ветки `server-build` тем же запросом, которым пользуется git: `https://github.com/kidw3st/pion.git/info/refs?service=git-upload-pack`. У REST API GitHub без ключа лимит 60 запросов в час на IP, а IP хостинга общий с чужими сайтами.
3. SHA уже выложен или помечен плохим после отката — выйти.
4. Скачать три файла с `raw.githubusercontent.com/kidw3st/pion/<SHA>/…`. Привязка к SHA обходит кэш GitHub — параметр `?t=` его не обходит (проверено 11 сентября).
5. **Проверить:** sha256 архивов совпадает с `build-info.json`; архивы распаковываются во временную папку; в архиве сайта есть `index.html`, `404.html`, `.htaccess`, `sitemap.xml`, `robots.txt` и нет файлов в защищённых путях (п. 6); в платёжном архиве нет `config.php`; каждый PHP-файл (платёжная часть и тема блога) проходит `php -l`. Хоть одна проверка не прошла — выкладка отменяется целиком, сайт остаётся прежним.
6. **Сайт:** список файлов сборки сервер составляет сам по распакованной папке (отдельный манифест от GitHub не нужен) → копирует файлы поверх веб-корня → удаляет файлы, которые были в списке прошлой сборки и пропали из нового, затем опустевшие папки. Без удаления устаревших файлов не заработают переадресации: Apache отдал бы старую страницу снятого с раздела букета. Удаляются только файлы, которые положила прошлая сборка. Никогда не трогаются `pay/`, `blog/` (кроме `blog/wp-content/themes/pion/`), `images/catalog/`, `images/showcase/`, `api/showcase.json`. Первая выкладка по новой схеме ничего не удаляет.
7. **`/pay/`:** только если архив изменился. Распаковка поверх, без удалений: `config.php`, `uds/`, `rate/` и логи в архив не входят и не трогаются.
8. Сохранить архивы и списки файлов трёх последних выкладок.
9. Записать состояние выкладки вне веб-корня: SHA, версия каталога и её `changedAt`, время выкладки. По нему админка показывает статус.

**Откат.** `php deploy.php --rollback` раскладывает предыдущую сборку и
помечает текущий SHA плохим, чтобы его не поставило следующим запуском.
Следующая новая сборка выкладывается как обычно.

**Пробный прогон.** `php deploy.php --dry-run` скачивает и проверяет, а
потом печатает, что бы сделал, ничего не меняя.

**Сторож.** Если сохранённая в админке версия каталога не выложена дольше
90 минут или выкладка падает, админка показывает «Выкладка задерживается», а
в служебный Telegram-чат из `config.php` уходит сообщение (не чаще раза в
3 часа). В чат заказов салона служебные сообщения не пишутся.

### 6. Изменения в сайте (Next.js)

- **Разделы из данных.** `CATEGORY_SLUGS` и `CATEGORY_LABELS` берутся из `data/catalog-meta.json`. Новый раздел — новая страница без правки кода.
- **Сетка каталога** строится из `tiles`.
- **Страница раздела** — букеты в продаже из этого раздела, в порядке раздела. Пустой раздел — «Сейчас здесь пусто» и ссылка на каталог.
- **Страница букета** — по адресу главного раздела, для статусов `active` и `hidden`. У снятого: пометка «Сейчас нет в продаже», нет кнопки «В корзину», есть похожие букеты из главного раздела, в разметке `availability: OutOfStock`. У букетов в продаже разметка как сейчас (`PreOrder`). Страницы снятых букетов остаются в карте сайта: так они не теряют позиции.
- **Ссылки и разметка** (карточки в сетке, `ItemList`, похожие букеты, «Букеты до 5000») всегда ведут на адрес по главному разделу — в каком бы разделе букет ни показывался.
- **Одноимённые букеты** (`getAmbiguousTitles`) считаются по uid, а не по разделам: букет в двух разделах не дубль.
- **«Букеты до 5000»** — как сейчас: букеты раздела «Букеты» дешевле 5 000 ₽, только те, что в продаже.
- **«Новинки» на главной** — первые три букета в продаже из раздела `novinki`, той же карточкой с пометкой NEW, что сейчас, но со ссылкой на страницу букета. В разделе пусто — блока нет. `site.newProducts` больше не используется.
- **Переадресации.** `data/redirects.json` уходит в сборку как `api/redirects.json`. Новое правило в `.htaccess` — по образцу правила для адресов Tilda: если по адресу вида `/<раздел>/<slug>/` нет `index.html`, запрос уходит в `pay/catalog-redirect.php`. Служебные папки (`blog`, `pay`, `api`, `images`, `md`, `_next`) правило не трогает. Тот ищет адрес в `api/redirects.json` и отвечает 301. Не нашёл — отдаёт `404.html` с кодом 404.
- **`api/catalog/*.json`, `api/index.json`, `llms.txt`, markdown-копии, карта сайта** собираются из тех же данных, что и сейчас. В `api/catalog` попадают только букеты в продаже. `tilda-map.json` ведёт снятые букеты на их страницу, удалённые — в раздел.
- **SEO разделов:** заполненные в админке поля, иначе шаблон, как сейчас.

### 7. Цены и заказы

- Цена при оплате берётся, как сейчас, через `catalog_index()` из `api/catalog/*.json` выложенной сборки — не из базы админки. Страница и корзина меняют цену одновременно, в момент выкладки.
- Заказать можно только букет в продаже: снятых в `api/catalog` нет. Если снятый букет остался у покупателя в корзине, оформление останавливается с понятным сообщением — какой букет убрать.
- «Новинки» становятся обычными букетами каталога, их цены приходят со сборкой. Дубль цен в `config.php` (`EXTRA_ITEMS`) после переключения убирается: менять цену в двух местах больше не нужно.
- Заказы в Posiflora, уведомления, акции, UDS, витрина — без изменений.

## Безопасность

- Пароли хранятся только как хэш (`password_hash`).
- 5 неверных попыток за 10 минут — вход заблокирован на 10 минут, отдельно по IP и по логину.
- Сессия: cookie `HttpOnly`, `Secure`, `SameSite=Strict`; новый идентификатор при входе; выход после 12 часов без действий.
- Каждая форма с CSRF-токеном. Изменения — только POST.
- Тексты экранируются при выводе. Запросы к SQLite — только с параметрами.
- Фото пересохраняются через GD: от исходного файла остаётся только картинка.
- Служебные PHP-файлы админки и `deploy.php` закрыты в `pay/.htaccess`, как сейчас `lib.php` и `sync-showcase.php`.
- Выгрузка каталога только читает, ничего не принимает.
- На сервере нет ключей GitHub, на GitHub нет секретов сайта.

## Журнал, копии, сбои

- **Журнал:** каждое изменённое поле — строка в `audit`.
- **Копии базы:** раз в сутки `VACUUM INTO` рядом с основным файлом, хранятся 30 дней.
- **Фото удалённых букетов** переносятся в `images/catalog/_deleted/` и стираются через 90 дней. Фото, заменённые новыми, — так же.
- **Сборка упала** — сайт не меняется. GitHub пишет владельцу репозитория, сторож на сервере — в служебный чат.
- **Выложилось, но плохо** — откат одной командой.
- **Нет связи с GitHub или с сервером** — следующая попытка через 15 минут. Ничего не теряется: каждый раз берётся последняя версия каталога.

## Перенос нынешнего каталога

1. `scripts/make-catalog-export.mjs` строит выгрузку из нынешних файлов репозитория:
   - 13 разделов: названия из `CATEGORY_LABELS`; обложки, тексты и «Не нашли нужное?» из `catalog-meta.json`; SEO-поля из `PAGE_SEO` для разделов, у которых они есть;
   - 12 плиток в нынешнем порядке. Пять разделов без плиток получают «Не показывать в каталоге»;
   - 487 букетов после `dedupeProducts`, все со статусом «в продаже» — сайт сейчас показывает и продаёт их все. 35 дублей и «Copy:» не переносятся: страниц у них и сейчас нет. Порядок — как в файлах;
   - раздел «Новинки» (`novinki`, без плитки в каталоге) и в нём три нынешние карточки с главной — «Пион», «ChocoMe», «Новинка!» — как букеты в продаже: те же названия, цены и фото, подпись становится составом. Их фото копируются из `images/site/` в `images/catalog/novinki/`. Своих страниц у карточек не было — теперь будут. Салон, скорее всего, заменит их настоящими новыми букетами.
2. **Проверка туда-обратно** (автотест): эта выгрузка, пропущенная через `apply-catalog-export.mjs`, даёт файлы, по которым собирается тот же сайт — те же 515 адресов в карте сайта с теми же ценами, фото и порядком плюс четыре новых: `/novinki/` и три страницы бывших карточек «Новинок». Блок «Новинки» на главной показывает те же три карточки.
3. `import-catalog.php` загружает выгрузку в базу на сервере. После этого `/pay/catalog-export.php` должен отдать выгрузку с той же версией — вторая проверка.
4. Workflow начинает брать каталог с сервера. Первая сборка из данных админки выкладывается под присмотром разработчика.
5. После первой выкладки из `config.php` убирается `EXTRA_ITEMS`.

Фото каталога не переезжают: они уже лежат на сервере по тем же путям.
Файлы каталога в репозитории остаются снимком для разработки.

## Тестирование

- **vitest:** `apply-catalog-export` — разделы, плитки, статусы, букет в нескольких разделах, адрес по главному разделу, переадресации, проверки выгрузки и защита от массовой потери; перенос туда-обратно. PHP: сравнение списков файлов — какие удалить, защищённые пути не трогаются никогда.
- **PHP-тесты** на GitHub Actions (PHP 8.2) на временной базе: создание, правка и удаление букета; черновик — нет в выгрузке, slug следует за названием до публикации, в черновик опубликованный не вернуть; снять и вернуть — адрес и место те же; восстановление удалённого; новый букет занимает адрес удалённого тёзки; предупреждение о тёзке; главный раздел по умолчанию не «Новинки»; uid и slug; переадресации при смене главного раздела и удалении, схлопывание цепочек; проверка цены; одновременная правка; выгрузка и стабильность версии; пароли, блокировка подбора, CSRF; пересохранение фото. `slugify` в PHP и JS дают одинаковый результат на названиях всех 487 букетов.
- **vitest для «Новинок»:** на главной первые три букета в продаже из раздела, снятые пропускаются, пустой раздел — без блока.
- **Сервер:** `deploy.php --dry-run`, первые выкладки — под присмотром разработчика.
- **Сквозная проверка** на боевом сайте без заказов: тестовый букет «снят с продажи» → страница с пометкой → удаление → переадресация в раздел.

## Этапы

Каждый этап — отдельный план работ и отдельная проверка. Начинаем с первого.

1. **Автовыкладка.** `deploy.yml` собирает сайт из `master` (каталог пока из файлов репозитория); `deploy.php` с проверками, списками файлов, откатом и сторожем; замена полуночного задания; `images/catalog/` выходит из архива сайта. Проверить в настройках репозитория, что GitHub Pages выключены. Результат: выкладка без ручных шагов, в том числе правок разработчика.
2. **Админка и формат выгрузки.** Первым делом — убедиться, что запросы с GitHub Actions доходят до `pionperm.ru`. Дальше вход, букеты, разделы, фото, журнал, статус выкладки, копии, `catalog-export.php`. Со стороны сайта — `apply-catalog-export.mjs`, разделы из данных, статусы, несколько разделов у букета, переадресации. Всё проверяется на выгрузке из нынешних файлов, сайт пока работает по-старому.
3. **Перенос и переключение** — по разделу «Перенос нынешнего каталога».
4. **Инструкция для салона** на одну страницу: как войти, добавить букет, подготовить черновик, поставить букет в «Новинки», снять с продажи и вернуть, создать раздел, что значат статусы выкладки.

Пока идут этапы 1–2, новые букеты по просьбе салона добавляет разработчик:
данные — в репозиторий, фото — сразу на сервер, потому что из архива сайта
фото каталога уже исключены.

## Не входит в объём

- Ручная сортировка букетов внутри раздела (кроме «новые сверху»).
- Варианты и размеры букета с разными ценами, остатки, скидки на отдельный букет.
- Правка текстовых страниц, слайдера на главной, акций.
- Плитки страницы «Цветы» (Розы, Пионы, Разные цветы) остаются как есть. Новый раздел показывается плиткой в каталоге.
- Импорт из Posiflora. Витрина работает как сейчас.
- Добавление сотрудников из админки.
